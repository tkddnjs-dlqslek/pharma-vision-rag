읽는 법:
- **검색 단계의 비전 우위가 답변 단계까지 남음**: vision이 text_rerank보다 전체와 차트 모두 유의하게 높고, 두 회차에서 점수가 똑같이 나옴.
- **agentic의 확실한 우위는 멀티홉**: 두 방식 모두 고정 방식에 멀티홉에서 한 번도 지지 않음(0승 12~18패).
  단일 검색이 못 푸는 "쌍둥이 페이지"와 "회사 쏠림"을 질의 분해와 문서 필터로 해결함.
- **BM25만 가진 E4는 전체로는 vision과 통계적으로 구별되지 않음.** 1회차에서는 p=0.03이었으나 2회차 점수가 0.87에서 0.81로 떨어져,
  두 회차 평균으로는 p=0.25. **1회차만 보고 "agentic이 vision을 이긴다"고 쓴 이전 결론은 철회함.**
- **비전 도구를 더한 E4b는 두 회차 모두 1위이고 vision을 유의하게 이김.** 우위는 멀티홉에서 오고, 차트는 vision과 동률(vision 단독의 차트 R@5가 이미 0.97).
- **본문 약점 보완은 재현되지 않음.** 1회차 E4b 본문 0.95(E4 대비 8승 1패, p=0.04)였지만 2회차는 0.78이고, 두 회차 평균으로 E4 대비 6승 3패(p=0.51).
  2회차의 한 에이전트가 BM25로 충분하다고 판단해 비전 도구를 한 번도 쓰지 않았고, 1회차에 비전 검색으로 찾았던 C04를 놓침. **도구 선택이 에이전트 점수 편차의 주원인.**
- **에이전트는 회차 간 편차가 큼**: 같은 셀이 두 회차에서 같은 점수를 받은 비율이 고정 방식 0.89~0.94, 에이전트 0.80.
  고정 방식은 페이지 3장이 정해져 있어 생성만 흔들리고, 에이전트는 검색 경로까지 매번 달라짐. 에이전트 비교는 반복 실행 없이는 믿기 어려움.
- **hybrid_rerank는 vision을 넘지 못함**: 검색 단계에서도 R@1이 0.58로 vision 0.64보다 낮았음. 상위 3장만 쓰는 생성 단계에서 그 차이가 드러남.
- **한국어 손실은 text 경로에서만 큼**(-0.12). vision은 -0.04, E4b는 -0.04, E4는 차이 없음.
- E4b 에이전트가 반복적으로 틀린 사례: A03(Roche 2024년 4분기 성장률)은 두 회차 모두 "2024년 문서가 없어 찾을 수 없음"으로 답함.
  실제 값은 2025Q1 덱의 성장률 추이 차트에 있음. "과거 값은 과거 문서에 있다"는 가정이 에이전트의 체계적 약점.

**채점 신뢰도**: 라운드마다 1차 채점분 40건을 기준점으로 섞어 채점자 편차를 잼. r2(E4b 1회차)는 기준점 36/40 일치, 답변당 +0.025,
r3(2회차 전체)는 39/40 일치, +0.013. 즉 E4b 1회차와 모든 2회차 점수는 r1보다 약간 후한 채점이며 그 폭은 0.01~0.03.
1차 채점(메인 세션이 직접 판정, agentic은 arm을 알고 채점)과 blind 재채점의 판정 일치율은 0.88~0.94, agentic 편향은 셀당 +0.008.

**정답 누출 점검**: 서브에이전트는 `CLAUDE.md`를 자동으로 읽는데, 2026-09-21까지 이 파일 핸드오프 절에 A01, A02, B08의 기준 정답 수치와
gold 페이지가 적혀 있었음(2회차 생성 에이전트가 이 파일을 언급해 발견, 즉시 삭제). 이 세 문항과 결함 문항 D03을 빼고 다시 계산해도
1회차 0.58 / 0.79 / 0.75 / 0.88 / 0.94, 2회차 0.59 / 0.79 / 0.78 / 0.82 / 0.91로 결론이 같음.

**그 밖의 한계**: 재채점 r1 묶음은 B08 기준 정답 수정(두 발행일 병기) 전에 만들어졌음(영향은 몇 셀). 채점자끼리 모호 기간 문항의 기준이 조금씩 달랐음.
도구 예산(질문당 10회) 초과는 1회차 E4 1셀, E4b 1셀. 초과 셀을 오답으로 치면 E4 0.86, E4b 0.92(1회차).
에이전트 도구의 BM25 문서 필터에 버그가 있었음: 전체 상위 50개 조각을 뽑은 뒤 문서로 걸러서, 지정 문서가 50위 밖이면 빈 결과를 냄.

**gold 이력**: 실패 분석(`docs/FAILURE_ANALYSIS.md`)의 누락 5문항(A02, A03, A05, A19, C05), 렌더로 확인한 A01과 B08, 그리고

인용했는데 gold에 없던 페이지 92개를 모아, 서브에이전트가 렌더된 페이지를 보고 기준 정답의 수치가 실제로 실렸는지 판정(57건 해당)하고,
메인 세션이 "그 페이지 하나로 질문이 묻는 걸 다 답할 수 있는가"(멀티홉은 해당 홉) 기준으로 다시 걸러 38페이지를 추가함(27문항).
제외 사례: 두 수치를 묻는데 하나만 실린 페이지, 재작성 전 값이 함께 실린 페이지(A02의 2024Q3 덱), 반올림 합계만 있는 경우 중 기간이 다른 것.
추가한 38페이지는 모두 페이지 텍스트에 핵심 수치가 있는지 교차 확인했고, 차트와 반올림 3건은 직접 렌더해 확인.

**gold 점검 전후 비교**: "gold 누락 때문에 텍스트 쪽이 과소평가됐다"는 의심은 **틀렸음**. 보완 후 R@5는 text 계열이 0.02~0.05,
vision이 0.04 올랐고, 가장 크게 오른 건 **vision의 멀티홉(0.42에서 0.62)**. 추가 38장 중 22장이 슬라이드였고,
R@5가 올랐다는 건 비전 경로가 그 페이지들을 이미 상위 5위 안에 올리고 있었는데 gold가 없어서 점수를 못 받았다는 뜻.

질의 단위 짝비교(R@5, 부호 검정): vision 대 text_rerank 전체 30승 7패(p<0.001), 차트만 11승 1패(p=0.006), 표만 7승 2패(p=0.18, 유의하지 않음).
vision 대 hybrid_rerank 5승 5패(차이 없음). text_bm25 대 text 15승 7패(p=0.13, 유의하지 않음).

읽는 법:
- **핵심 가설은 검색 단계에서 지지됨**: 텍스트 경로를 청킹 개선, 리랭커, 키워드 검색으로 강화해도 차트 문항에서 비전과의 격차가 남는다(0.70~0.80 대 0.97).
- **BM25는 단독으로 가장 약하고, dense와 섞으면 방향은 개선이지만 유의하지 않음**(15승 7패, p=0.13).
  한국어 질의는 영문 코퍼스와 겹치는 토큰이 제품명과 숫자뿐이라(bm25 한국어 R@5 0.39) 섞으면 한영 격차가 벌어짐(text 7%p에서 text_bm25 14%p).
- **표와 본문은 격차가 작거나 없음**. 표는 방향은 비전 우위지만 이 표본 크기에서는 유의하지 않음.
- **고정 가중치 RRF는 비전 단독의 R@1을 넘지 못함**(0.58 대 0.64). R@5와 표, 본문은 hybrid_rerank가 가장 높음.
- **멀티홉은 vision 0.62, 텍스트 계열 0.34~0.43**. 단일 검색으로는 여전히 절반 안팎. 실패 분석에 따르면 원인이 둘로 갈림: 한 회사의 여러 분기를 묻는 문항은
  전년도 쌍둥이 페이지가 자리를 차지하고, 여러 회사를 비교하는 문항은 상위 5장이 한 회사로 쏠림. 둘 다 E4(agentic)의 문서 필터와 질의 분해가 겨냥하는 문제.
- 리랭커는 표 문항의 R@1을 깎음(0.40에서 0.25, R@5는 0.72에서 0.78로 오름): 표 구조는 잘 맞추지만 연도와 분기 토큰을 dense보다 약하게 반영해,
  쌍둥이 표 중 틀린 분기를 1위에 올리는 경우가 늘어남.
- 한국어 질의는 모든 변형에서 영어보다 낮음. 격차는 hybrid_rerank와 vision이 가장 작음(5%p).

**비전 검색 설계 변경**: 페이지당 패치 벡터 전체를 Qdrant 멀티벡터로 넣으면 1,709p에 약 24GB(fp32). 벤치마크는
질의가 고정이므로 `.npy` 원본을 한 번 훑으며 전 질의의 MaxSim을 정확히 계산함(벡터 DB 없음, 근사 없음).
대화형 앱용 2단계 검색(페이지 평균 벡터로 후보 추림 후 MaxSim)은 이 정확한 순위를 기준으로 검증할 후속 과제.

**데이터 보존 원칙**: Qdrant는 파생 인덱스일 뿐. 기준 데이터는 `data/pdf/`, `data/embeddings/text_blocks.jsonl`,
`data/embeddings/v2/`(RunPod 산출물: 순위, 텍스트 벡터와 청크, 질의 임베딩). 페이지 패치 임베딩 18.9GB는 내려받지 않았고
`runpod_input.zip`과 `embed_pages_gpu.py`로 약 $2, 1시간에 재생성한다. **질문 문구를 바꾸면 질의 임베딩과 순위를 다시 계산해야 함.** 2026-09-19에 Windows 바인드 마운트 볼륨에서 벡터가 전부 0이 되는 사고가 있었고
compose를 named volume으로 변경함.

- 인턴 업무에서 실제 나올 법한 질문으로 (면접 토킹 포인트).
- 외부 리뷰어 1명이 한국어 질문 품질 검토 (plan.md 요건 유지).
- 정답 수치는 통화·단위·기간까지 verbatim (`€3.5 billion`, `+20.3% CER`).

### 3.3 E4: agentic 모드 (2026-09-20 추가, 기준선 확보 후 착수)

**왜**: 고정 파이프라인의 실패 유형이 "한 번 검색하고 끝"이라는 구조에서 나온다. v1 벤치마크에서 확인한 것:
1위 오답의 상당수가 분기나 연도만 다른 쌍둥이 페이지, 멀티홉(D)은 상위 5장에 모든 홉이 들어오지 않음,
기간이 모호한 질문은 아무 분기나 가져옴, hybrid의 라우터는 키워드 if문. 코퍼스 v2(1,709p, 4개사, 2개 연도)에서 더 심해진다.
**위치**: 기존 4모드를 대체하지 않고 **다섯 번째 비교 대상**으로 추가한다. 같은 60문항으로
"고정 파이프라인 대비 정답률이 얼마나 오르고 비용과 시간이 몇 배 드는가"를 측정한다.
이 모드에 한해서만 대외 문서에서 "agentic"이라는 표현을 쓴다.

**구조**: Claude의 tool use로 직접 구현(LangGraph 불필요). 모델은 답변 생성과 같은 Sonnet. 최대 도구 호출 10회.

| 도구 | 입력 | 동작 |
|---|---|---|
| `list_documents` | 없음 | `eval/corpus.json`의 문서 id, 회사, 기간, 종류, 페이지 수 |
| `search_text` | query, 선택적 문서 id 필터 | `pharma_text` dense 검색 후 리랭커, 상위 청크와 (문서, 페이지) |
| `search_pages` | query, 선택적 문서 id 필터 | `pharma_caption` 검색. 차트 페이지로 가는 다리 역할 |
| `open_page` | 문서 id, 페이지 | 페이지 이미지를 렌더해 모델에 보여줌. 차트는 여기서 읽음 |
| `calculate` | 수식 | 증감액, 비율. 환각 방지용 |
| `final_answer` | 답변, 인용 페이지 목록 | 종료 |

비전(Nemotron) 검색은 도구로 넣지 않는다. agent가 즉석에서 만든 검색어는 미리 임베딩할 수 없고, 3B 모델을 개발 PC의
CPU(RAM 16GB)로 돌릴 수 없기 때문. GPU 엔드포인트를 상시로 띄울 수 있게 되면 `search_vision`을 추가하는 것이 후속 과제.

**측정**:
- 정답 일치(Haiku judge, 3회 평균). 기존 모드와 같은 기준
- 인용 페이지의 gold 적중(`final_answer`의 인용 목록을 `eval/metrics.py`의 그룹 기준으로 채점)
- 질문당 도구 호출 수, 입력과 출력 토큰, 비용, 소요 시간
- 유형별(A, B, C, D), 기간 명시 여부별, 한/영별 재집계. 가설: D와 ambiguous에서 가장 크게 오르고 C는 차이 없음

**비용 추정**: 질의 120개 × 호출 5~10회 × 3회 반복. 프롬프트 캐싱 전제 약 $15~30. 실제 값은 10문항 파일럿으로 먼저 확인.
**선행 조건**: `ANTHROPIC_API_KEY`, `pharma_text`와 `pharma_caption`의 v2 인덱스, E1 기준선 결과.
**산출물**: `src/pharma_vision_rag/modes/agentic.py`, `eval/runner.py`의 생성 단계에 mode 추가, `docs/REPORT.md`의 비교 절.
**하지 않는 것**: 멀티 에이전트, 장기 메모리, 웹 검색. 단일 agent와 다섯 도구로 한정한다.

## 4. 인프라 선행 과제 — 비전 인덱싱 경로 교체 (🔶 코드 완료, 실행 대기 — 2026-09-16)

**문제**: 현재 `retriever/nemotron.py`는 Colab FastAPI 터널에 페이지 이미지를 보내고 `[N_patches, 3072]`
임베딩(~14MB/페이지)을 받아온다. Cloudflare 무료 터널이 30MB에서 502를 내고 throughput이 페이지당
~3분이라 172p 인덱싱이 사실상 불가능하다.

**해법**: 임베딩을 인터넷으로 왕복시키지 않는다.

1. ✅ `scripts/embed_pages_gpu.py` — **RunPod**(Colab 아님, 09-16 결정) GPU 박스에서 단독 실행. PDF 7개 →
   전 페이지 `render_scale=1.5` 렌더 → Nemotron 3B `forward_images` 배치 → `pages/<source>/<page>.npy`(fp16) +
   `queries/<id>_<ko|en>.npy` 60개 + `manifest.json` → `embeddings.zip`. 재실행 시 기존 `.npy` 건너뜀.
   (예상: 4090 약 10분, T4급 약 15분. zip 약 2.4GB)
2. ✅ `scripts/13_load_nemotron_npz.py` — zip 해제 → `NemotronVisionRetriever.qdrant.upsert` (gRPC)로 로컬 업서트.
   포인트 ID는 기존 `_page_id(source, page)` 재사용 → idempotent. 더미 임베딩으로 스모크 테스트 통과.
3. ✅ 쿼리 임베딩 60개도 같은 스크립트에서 뽑아 zip에 포함 → 벤치마크 중 GPU 의존 없음.
   `eval/runner.py`(순서 6)는 `data/embeddings/<zip이름>/queries/`를 읽는 오프라인 쿼리 클라이언트를 쓴다.

`06_index_nemotron.py`(터널 방식)는 docstring에 deprecated 표기. `02_nemotron_tunnel.ipynb`는 fallback으로만.

## 6. 지표와 보고 규칙

**검색**: Recall@1/3/5, NDCG@5 — gold_pages 기준. ambiguous 질문은 gold 중 하나라도 잡히면 hit.
**생성**: 정답 일치 (Haiku judge: 수치·단위·기간 일치 여부 3단계 — 정답/부분/오답). 3회 평균.
**비용**: 인덱싱 $/페이지, 쿼리 $/질문, 저장 용량 (모드별).

보고 규칙 (30문항 벤치마크의 정직성 확보):
1. 집계 %와 함께 **질문별 30행 결과표를 그대로 공개** — "어떤 질문에서 갈렸는가"가 진짜 콘텐츠.
2. 생성 지표는 **평균 ± 범위(3회)**로 표기.
3. **3문항(10%p) 이내 차이는 유의하지 않음**을 리포트 서두에 선언.
4. 실패 케이스 10개는 원인 태그: OCR/레이아웃 손실 · 리트리버 miss · 리랭커 강등 · VLM 환각 · 언어 mismatch · 기간 혼동.
